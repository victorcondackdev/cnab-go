# cnab-go

[![CI](https://github.com/victorcondackdev/cnab-go/actions/workflows/ci.yml/badge.svg)](https://github.com/victorcondackdev/cnab-go/actions/workflows/ci.yml)
[![Go Reference](https://pkg.go.dev/badge/github.com/victorcondackdev/cnab-go.svg)](https://pkg.go.dev/github.com/victorcondackdev/cnab-go)

A zero-dependency Go library for FEBRABAN CNAB files, the fixed-width
formats Brazilian banks use to register boletos (*remessa*), report
payments back (*retorno*) and exchange payment instructions.

Layouts are declared as plain structs with positions copied straight from
the bank manuals. The codec checks those declarations the first time they are
used, so a typo in a position fails a unit test instead of producing a file
the bank rejects three days later.

```go
type SegmentP struct {
    cnab240.DetalheControle                    // positions 1-13
    Segmento    string           `cnab:"14,1,const=P"`
    // ...
    NossoNumero string           `cnab:"38,20,alfa"`
    Vencimento  time.Time        `cnab:"78,8,date"`
    Valor       int64            `cnab:"86,15,money"` // cents
    // ...
}
```

## Why

- **Declarative layouts.** A record is a struct; a bank is a set of structs.
  No hand-written slicing, no offset arithmetic spread across the codebase.
- **Layout self-validation.** Every position from 1 to the record length must
  be covered by exactly one field. Gaps, overlaps, out-of-range positions,
  malformed tags, format/type mismatches and integer fields too wide for
  their Go type are reported together, by field name:

  ```
  fixedwidth: invalid layout Typo: overlap: Banco (1-3) and Lote (3-6); gap at 7-7 between Lote and Tipo
  ```
- **Exact money.** Amounts are `int64` cents end to end. No floats, no
  rounding, totals that add up.
- **Positional errors.** Every decoding problem carries the line, field name,
  1-based positions and offending value, and matches sentinel errors with
  `errors.Is`:

  ```
  cnab: line 3: field Valor (86-100) value "00000000000A000": must contain only digits
  ```
- **Lossless round trips.** `Write(Parse(file))` reproduces the samples byte
  for byte; unknown segments are carried through untouched.
- **Reconciliation.** Match a retorno against the boletos you expect and get
  every difference explained: paid exact, paid with interest or discount,
  paid late, divergent, duplicate, unknown, rejected, still open.
- **Standard library only.** No dependencies, Go 1.22+.

## Quick start

### Build a remessa

```go
company := file.Company{
    Nome: "Acme Utilidades Ltda", Documento: "11.222.333/0001-81",
    Agencia: "01234", Conta: "000000056789", ContaDV: "0",
}
bank := file.Bank{Codigo: "341", Nome: "Banco Itaú S.A."}

r := file.NewRemessa(company, bank).WithNSA(42).
    AddBoleto(file.Boleto{
        NossoNumero:     "00000001",
        NumeroDocumento: "NF-1001",
        Vencimento:      time.Date(2026, 12, 10, 0, 0, 0, 0, time.UTC),
        Valor:           150000, // R$ 1.500,00
        JurosPorDia:     50,
        Pagador: file.Pagador{
            Nome: "João da Silva", Documento: "529.982.247-25",
            Endereco: "Rua das Laranjeiras, 1500", Bairro: "Laranjeiras",
            CEP: "22240-003", Cidade: "Rio de Janeiro", UF: "RJ",
        },
    })

out, _ := os.Create("remessa.rem")
defer out.Close()
if _, err := r.WriteTo(out); err != nil {
    log.Fatal(err) // every invalid boleto is listed, with its index
}
```

The builder validates CPF/CNPJ check digits, CEP and amounts, folds accents
("João" becomes "JOAO") and truncates long names explicitly. Batch numbers,
record sequences and trailer counts are generated by `file.Write`; you never
maintain them by hand.

### Parse a retorno and reconcile

```go
f, err := file.Parse(in) // validates counts, sequences and structure
if err != nil {
    log.Fatal(err)
}
expected := []reconcile.Expected{
    {NossoNumero: "1", Valor: 150000, Vencimento: due},
    // ... loaded from your database
}
rep, err := reconcile.Reconcile(expected, reconcile.EntriesFromFile(f))
if err != nil {
    log.Fatal(err)
}
fmt.Print(rep.Summary())
```

`rep.Results` holds the same information as structured data. Nosso número
values are matched after stripping spaces and leading zeros, since banks pad
the field differently in remessa and retorno. `Options{GraceDays: n}`
tolerates payments on the next business day after a weekend due date.

The expected CSV has a header row with `nosso_numero`, `valor` (`1234.56` or

## Field formats

| Tag format      | Go type          | Encoding                                                                 |
|-----------------|------------------|--------------------------------------------------------------------------|
| `num`           | `string`, ints   | digits, right-aligned, zero-padded; blank decodes as `""`/`0`            |
| `alfa`          | `string`         | left-aligned, space-padded, upper-case ASCII with accent folding         |
| `raw`           | `string`         | left-aligned, space-padded, byte-exact (bank-reserved areas)             |
| `date`          | `time.Time`      | width 8 `DDMMYYYY`, width 6 `DDMMYY`; zeros or blanks are the zero time  |
| `money`         | ints (cents)     | digits with two implied decimals; negative values rejected               |
| `const=X`       | `string`         | fixed literal, verified on decode                                        |

Positions are `start,length` or `start-end`, 1-based and inclusive, exactly as
printed in bank manuals. Values that do not fit are errors, never silently
truncated.

## Adding a bank layout

1. Write one struct per record type, one field per row of the manual,
   including the filler rows ("Uso exclusivo FEBRABAN/CNAB"):

   ```go
   type DetalheRetorno struct {
       Registro    string    `cnab:"1,1,const=1"`
       // ... every position up to 394
       NossoNumero string    `cnab:"63,8,num"`
       Ocorrencia  int       `cnab:"109,2,num"`
       DataPgto    time.Time `cnab:"111,6,date"`
       ValorPago   int64     `cnab:"254,13,money"`
       // ...
       Sequencial  int       `cnab:"395,6,num"`
   }
   ```
2. Add a test that pins the layout:

   ```go
   func TestLayout(t *testing.T) {
       if err := fixedwidth.Check(DetalheRetorno{}, 400); err != nil {
           t.Fatal(err) // names every gap, overlap and bad tag
       }
   }
   ```
3. Decode with `fixedwidth.Unmarshal(line, &rec)`, or for CNAB 400 files
   `file.Parse400` followed by `detail.Decode(&rec)`.

Shared prefixes are declared once and embedded (see `cnab240.Controle` and
`cnab240.DetalheControle`). [`cnab400/bradesco`](cnab400/bradesco) is a
complete example.

## Supported layouts

| Layout | Records | Status |
|---|---|---|
| CNAB 240 cobrança (FEBRABAN generic) | file header 0, batch header 1, segments P, Q, R, T, U, batch trailer 5, file trailer 9 | Implemented from the FEBRABAN generic layout (v08.x–v10.x share these positions). Bank-reserved areas and code tables vary per bank. |
| CNAB 240, other segments (A, B, J, Y, S, ...) and record types 2/4 | | Preserved verbatim as `RawSegment`; not typed yet. |
| CNAB 240 pagamentos (SISPAG-style payment files) | | Roadmap. The codec supports them; the structs are not written. |
| CNAB 400 cobrança, generic | header 0, detail, trailer 9 | Skeleton only: record type, sequence numbers and the common header fields. Details must be decoded with a bank-specific struct. |
| CNAB 400 Bradesco (237) remessa detail | type 1 | Experimental, from the public manual; not homologated. |
| CNAB 400 retorno layouts (any bank) | | Roadmap. |

Only movement codes whose meaning is identical across the FEBRABAN generic
layout are declared as constants (`cnab240.RemessaEntrada`,
`cnab240.RetornoLiquidacao`, ...). Rejection reason codes (*motivos*) are
returned as raw two-character codes because their meaning is bank-specific.

## Performance

Parsing a 10,000-line CNAB 240 retorno (2.4 MB) takes about 17 ms with two
allocations per line on a 2-vCPU Xeon; writing it back takes about 14 ms
(`go test ./file -bench . -benchmem`).

## Testing

```sh
go test -race ./...
go test ./file -run '^$' -fuzz FuzzParse -fuzztime 30s
```

The suite covers each format and error path, byte-level position checks of
the sample files taken directly from the manual (independent of the struct
tags), `Unmarshal(Marshal(x)) == x` and `Write(Parse(f)) == f` round trips,
and fuzz targets for the codec, segment decoding and whole-file parsing.
Sample files in [`file/testdata`](file/testdata) use fictitious companies,
accounts and documents.

## Disclaimer

CNAB layouts are defined by FEBRABAN and, in practice, by each bank's own
manual, which may restrict codes, redefine reserved areas or deviate from the
generic layout. Always validate generated files against your bank's manual and
homologation environment before going to production. This project is not
affiliated with or endorsed by FEBRABAN or any bank.
